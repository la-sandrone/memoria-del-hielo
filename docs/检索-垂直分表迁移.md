# 检索垂直分表与分词 v2：迁移手册

> 对象：`documents_book_chunk`（原 654,315 行 / **真实占盘 25 GB**）
> 工具：`tools/split_memoria.py`（离线、人工运行、可急停、可续跑）
> 日期：2026-11-07 · 与 melquiades 那场「dsh_message 重建与垂直分表」同源

---

## 一、为什么拆（实测，不是估算）

`information_schema` 报这张表 13,084 MB —— **这个数字是错的**，InnoDB FULLTEXT 的
影子文件不计入它。真实占盘：

| 文件 | 大小 |
|---|---|
| `documents_book_chunk.ibd` | 12.70 GB |
| `documents_book_chunk#i#04.ibd` | 1.85 GB |
| `FTS_...0862_INDEX_1 / _6`（一个 FULLTEXT 的影子） | 2.74 + 1.86 GB |
| `FTS_...0869_INDEX_1 / _6`（另一个 FULLTEXT 的影子） | 0.65 + 2.84 GB |
| 合计（不含书表与缓存） | **约 22.6 GB** |

列级权重（723 行分层抽样，投影到全表）：

| 列 | 每行 | 全表 |
|---|---|---|
| `content` | 3,337 B | ≈ 2.0 GiB |
| `content_tokenized` | 3,187 B | ≈ 1.9 GiB |
| `embedding` VECTOR(1024) | 4,096 B | ≈ 2.5 GiB |

**行宽 ≈ 10.6 KB ⟹ 一个 16 KB 页只装约 1.5 行。** 而向量路因为 JOIN 让 HNSW 失效、
走的是精确扫描 —— 它每读一行要搬 10.6 KB，其中只有 4 KB 是向量。这是分表最硬的理由，
比"省磁盘"硬得多。

## 二、目标形态

```
documents_book_chunk      元数据 + content        uq_book_seq + FK(→documents_book)
documents_book_chunk_fts  content_tokenized       FULLTEXT（查询走 NL MODE）
documents_book_chunk_vec  embedding               VECTOR INDEX (HNSW, cosine)
```

三条设计取舍：

1. **侧表不带外键。** 外键会让 `RENAME` 切换被拦住。代价：删书必须显式删三张表
   —— `src/cli/mhi_remove_book.py` 已改成「侧表 → 主 chunk → 脚注 → 书目」的显式顺序。
2. **`content` 上的 FULLTEXT 退役。** `content_tokenized` 是它的投影，查询侧统一
   打 tokenized（汉字 bigram + 非汉整词），索引只留一份 ⟹ 省掉一整代 FTS 影子文件。
3. **主表保留 `AUTO_INCREMENT`。** 导入器要靠它分配 chunk_id，侧表按它挂靠。

## 三、怎么跑

在项目根目录，**按顺序**，一步一跑：

```bash
python3 tools/split_memoria.py preflight              # 只读体检，先跑这个
python3 tools/split_memoria.py create                 # 建三张影子表
python3 tools/split_memoria.py prune --confirm-prune-orphans   # ← 见「四、坑 3」，加 FK 前必须
python3 tools/split_memoria.py fill                   # 灌数据（可续跑）
python3 tools/split_memoria.py index                  # 建 4 个索引（HNSW 最慢）
python3 tools/split_memoria.py cache                  # embedding_cache: JSON → VECTOR
python3 tools/split_memoria.py verify --deep           # 计数/分书/抽样/分词/LIKE 对拍
python3 tools/split_memoria.py switch --confirm-switch # 原子 RENAME
# 观察几天后：
python3 tools/split_memoria.py cleanup --confirm-drop-old
```

随时可看进度：`python3 tools/split_memoria.py status`。

### 各步实测耗时（本机 16 GiB buffer pool）

| 阶段 | 实测 |
|---|---|
| 主表直搬（服务端 `INSERT … SELECT`） | 654,315 行约 **60 秒**（15–19k 行/秒） |
| 向量表直搬 | 约 **30 秒** |
| 分词重算（唯一走网络的一趟，批 500） | 实测 **651,206 行用 8 分 12 秒**（约 1,070 chunk/秒；早期小批量峰值 3.1k/s 不可外推） |
| UNIQUE / FK | 秒级 ~ 十几秒 |
| FULLTEXT | 十几秒 ~ 数分钟（取决于行数） |
| **HNSW（65 万 × 4 KB）** | 实测 **89 分钟**（12:27:20 → 13:56）。其中 copy 阶段约 87 分钟、收尾 2 分钟。瓶颈是**行 copy**，不是建图 |

**磁盘预算**：这条 ALTER 需要**额外 5 GB+ 临时空间**（实测临时段合计 5.10 GB）。
按「原表大小 × 1.5」留余量 —— 65 万行的向量表 3.39 GiB ⟹ 至少留 5.5 GiB 空闲。
空间不足会得到一个难看的 ALTER 失败，而不是提前拒绝。

**落盘结果（实测，两个都是反直觉的）**：

| 文件 | 大小 | 说明 |
|---|---|---|
| `documents_book_chunk_vec_new.ibd` | 3,636,461,568 B | **与改前字节数完全相同** —— 别拿"大小变了没有"当成功判据 |
| `documents_book_chunk_vec_new#i#01.ibd` | 1,853,882,368 B | **HNSW 索引在这里**，不在主 `.ibd` 里 |

⟹ 这次 ALTER 的真实磁盘代价 = 原表大小 **+ 1.73 GiB 索引**。

**⚠️ HNSW 的进度怎么看（实测修正）**：`ALTER TABLE … ADD VECTOR INDEX` 在 MariaDB 12.3.2
上走的是 **copy algorithm（整表重建）**，所以

- **目标表 `documents_book_chunk_vec_new.ibd` 全程不增长**（12:28 到 13:05 一直是 3.39 GiB）
  —— 拿它判进度会**误判成卡死**；
- 真正在写的是**同目录的 alter 临时表**：
  `#sql-alter-<id>-<hash>-0.ibd`（行数据，2.29/3.64 GB ≈ 63% 处）
  与 `#sql-alter-…-0#i#01.ibd`（HNSW 索引临时文件）；
- `PROCESSLIST` 里该连接 `STATE='copy to tmp table'`、`TIME` 持续递增，就是活着。

判据：`ls -la <datadir>/#sql-alter-*` 这两个文件在长 = 在干活。

实测曲线（654,315 行，08:27 起跑）：

| 时刻 | `#sql-alter-*-0.ibd`（行数据） | `#sql-alter-*#i#01.ibd`（HNSW） | PROCESSLIST TIME |
|---|---|---|---|
| +16 分钟 | 1.89 GB | 0.97 GB | 958 s |
| +32 分钟 | 2.54 GB | 1.30 GB | 1,930 s |
| +52 分钟 | 2.98 GB | 1.52 GB | 3,122 s |
| +77 分钟 | **3.38 GB（93%）** | **1.72 GB** | 4,607 s |

注意速率会**衰减**（0.45 MB/s → 0.21 MB/s）：越往后越慢，别拿前期速率外推 ETA。
再说一遍：**目标表 `.ibd` 全程不变**（本例从 12:28 到 13:44 一直是 3,636,461,568 B）。
（归档那场同源工作的结论一样：InnoDB 的 `PROGRESS` 只在 merge sort 阶段上报，
`TMP_SPACE_USED` 明确不含 ALTER，最后只能靠临时表文件大小。）

## 四、三个坑（都是本次实测踩出来的，都已修在工具里）

### 坑 1 · 水位线用 UPDATE 写 ⟹ 永远 0
批次循环里原来写 `UPDATE _split_state SET watermark=? WHERE phase=?`。进度行在第一次
写入前**并不存在**，UPDATE 静默影响 0 行 ⟹ 水位线永远是 0 ⟹ 续跑从 0 重来，撞
`Duplicate entry for key 'PRIMARY'`。
**修法**：同事务 `INSERT … ON DUPLICATE KEY UPDATE`（`upsert_progress`），
外加一道自愈：水位线为 0 但目标表已有数据时，按 `MAX(chunk_id)` 续跑。

### 坑 2 · KILL 打了空靶
急停时要「KILL 服务端语句」，但原来登记的是 `one("SELECT CONNECTION_ID()")` ——
那是一次性连接，查完即关。真正在跑的是后面那趟自己的连接。
**修法**：每条长语句在执行前用**同一条连接**登记 `CONNECTION_ID()`；急停时扫
`_split_state` 里所有 `status='running'` 的连接，逐个确认在 PROCESSLIST 里再 KILL。
配套：**子进程忽略 SIGINT**（否则它先死、连接先断、服务端语句变僵尸 ——
归档那场实测过「断连 ≠ 取消」，客户端断开后服务端继续跑 698 秒并持元数据锁）。

### 坑 3 · 活库里根本没有那个外键
`scripts/init_db.sql` 声明了 `fk_chunk_book`，但 `information_schema` 里活库只有
`bucket_config` 与 `page_footnotes` 两条外键。**`mhi_remove_book` 依赖的
`ON DELETE CASCADE` 从来没生效过** —— 已攒下 **3,109 行孤儿 chunk**
（全部指向一本已删除的书）。加 FK 前必须先清，否则 ALTER 直接失败
（`Cannot add or update a child row`）。
**修法**：新增 `prune` 阶段（主表按 `book_guid`、侧表按"主表里没有这个 chunk_id"），
且 `index` 会先查孤儿并拒绝继续。

## 五、急停与回滚

- **Ctrl+C**：先 KILL 服务端语句，再收子进程，最后把状态标 `interrupted`。
  若仍有活连接，工具会打印 `kill --conn <ID>` 让你手动收尾 —— **不要跳过这一步**，
  否则一条僵尸 `ALTER` 会持元数据锁，后续所有 ALTER 都在
  `Waiting for table metadata lock` 排队。
- **续跑**：同一条命令再跑一次即可（水位线不丢、不会撞主键）。
- **回滚（switch 之后）**：把那条 `RENAME` 反过来执行；旧表
  `documents_book_chunk_old_<时间戳>` 在观察期内不要删。

## 七、清理旧表（观察期结束后）

切换后旧表被 RENAME 成带时间戳的名字，观察几天确认检索正常，再删。**先演练**：

```bash
cd <project-root>

# ① 演练：列清单 + 过安全闸，不删任何东西
python3 tools/split_memoria.py cleanup --dry-run

# ② 真删（带二次确认标志）
python3 tools/split_memoria.py cleanup --confirm-drop-old
```

**安全闸**（`cleanup` 内置，任一不通过就拒绝执行）：
三张活表行数一致且 > 0 · 书目表非空 · 活主表无孤儿 · 全文侧表有 FULLTEXT · 向量侧表有 VECTOR。
理由：旧表是**最后一份能切回旧结构的副本**，活表没就绪时删它等于把退路烧了。

**实测能回收多少**（2026-11-07 那次，`information_schema` 只会报 13.63 GB，是少算的）：

| 文件 | 大小 |
|---|---|
| `documents_book_chunk_old_<ts>.ibd` | 11.83 GiB |
| `documents_book_chunk_old_<ts>#i#04.ibd`（它的 FTS sidecar） | 1.73 GiB |
| 旧表的 **两代** FULLTEXT 影子 `FTS_…04a2_…0862/0869_INDEX_1/_6` | 2.55 + 1.73 + 2.64 + 0.61 = **7.53 GiB** |
| `embedding_cache_old_<ts>.ibd` | 0.90 GiB |
| **合计** | **≈ 22 GiB** |

那 7.53 GiB 是**最大的一块，而且在 `information_schema` 里完全看不见** —— 删旧 chunk 表才释放它。

**删之前必须有的东西**：一份**含旧表**的全库备份（见 `docs/备份与恢复.md`）。
删之后要回退，就只剩「从那份备份恢复」这一条路了。

**不在这条命令范围内的**：`documents_book_chunk_orphans_<日期>` —— 那是被清掉的
3,109 行孤儿 chunk 的唯一副本（删书残留的死数据），要不要留自己定：

```sql
-- 确认不再需要后：
DROP TABLE documents_book_chunk_orphans_20261107;
```

## 八、已知代价（不要当 bug 报）

1. **NL MODE 比 BOOLEAN 慢**，而且**端到端比单路更慢**。切换后实测（10 条真实查询）：

   | 走法 | 时延 | 说明 |
   |---|---|---|
   | 全文路（NL） | ≈ 3,000 ms | 真的在给几万行打分；旧 BOOLEAN 只要 13 ms —— 因为它 0 命中 |
   | 向量路（精确扫描） | ≈ 1,650 ms | JOIN 让 HNSW 失效，走精确 KNN（无近似损失） |
   | 双路（默认） | ≈ 4,550 ms | ≈ 两者相加；rerank 几乎不占 |
   | 端到端（含书级聚合/去重/精排） | **2.4–6.1 s，平均 6.7 s** | `tools/search_bench.py` 实测 |

   MCP 工具超时是 300 s，不受影响；但**交互体感上这是这次改动最明显的退化**。
   要压的话首选项是向量路（去掉 JOIN 换 HNSW 近似，可到几十 ms —— 但会引入约 8% 的
   top-1 漏检，是否接受要单独定）。详见 `docs/待办-检索下一版.md`。
2. **子串兜底（LIKE）在 65 万行上约 16 秒**。所以它**只在全文与向量都空的时候**才跑
   （`_book_search` 里 `if not merged`），常态查询不付这个代价。
3. **非 CJK 查询不再走 `content` 列**：那个 FULLTEXT 退役了。拉丁/俄文/希腊文在
   `content_tokenized` 里是整词，照常命中。
