## 1. 剪枝从「手工词表」升级成「按文档频率自动判」（数据层）

**现状**：停词表是内置的一份单字表（的/了/在/是/和…），配置可用
`[search].stopwords` 覆盖。剪枝规则是「整词每个字都是停词才丢」——
比第一版的「任一单字命中就丢」安全得多，但仍是**人拍脑袋定的**。

**为什么推迟**：当前 65 万 chunk 的规模下，NATURAL LANGUAGE MODE 的 **idf 已经在替
词表干活**（`的世`、`没的` 这类高频 bigram 的 idf 极低，对打分贡献近乎 0）。
手工词表在这个规模上带来的收益主要是「查询串更短」，不是「排序更好」。
真正的收益要等语料明显长大才显现。

**要做什么**：
1. 建一张 `token_df(token VARCHAR(64) PK, df INT UNSIGNED)` 快照表。
2. df 的算法（不需要分词重算，直接打 FULLTEXT）：
   `SELECT COUNT(*) FROM documents_book_chunk_fts WHERE MATCH(content_tokenized) AGAINST(? IN BOOLEAN MODE)`
   —— 每个候选 token 一条，几百个 token 在秒级。
3. 剪枝判据从「在词表里」换成「df / 总行数 > 阈值」（建议先取 20%）。
4. 快照按语料版本重建（导入新书后重算），并记进 `_split_state` 或独立表。

**怎么量收益**：用 `tools/search_bench.py --json` 前后各跑一次，比
每条的 top-3 书名与耗时；再用 `docs/真实检索查询分布案例.md` 里的空手案例当回归集。

**风险**：df 阈值本身也会误杀（一个高频但确实有区分力的词）。所以落地时必须
保留现在已经有的两道保险：**全被剪时退回未剪词表** + **0 命中时用未剪词表重试一层**。

## 3. （备忘）本轮的「已知代价」里哪几条值得再压

| 代价 | 现状 | 值不值得治 |
|---|---|---|
| 端到端 2.4–6.1 s（平均 6.7 s） | 切换后实测，构成见下 | **最值得治的一项**，详见下节 |
| LIKE 兜底约 16 s | 只在其它路全空时跑 | 不值得：它是兜底，不是主路径；真要压可加 chunk_id 分区扫描 |
| HNSW 建索引 89 分钟 | 一次性迁移成本（实测） | 不值得：只在迁移时付一次 |

### 时延：钱花在哪（实测拆解，一条真实查询）

| 走法 | 时延 | 备注 |
|---|---|---|
| 全文路（NL MODE） | 2,979 ms | 给几万行打分；旧 BOOLEAN 13 ms 但 0 命中 |
| 向量路（精确扫描） | 1,652 ms | JOIN 让 HNSW 失效，走精确 KNN |
| 双路（默认） | 4,550 ms | ≈ 两者相加，rerank 不占 |

两条可选路：

1. **向量路换近似**（收益最大）：去掉内层 JOIN 让 HNSW 生效，1.65 s → 几十 ms。
   代价：HNSW 自查询 top-1 命中率 92%（top-10 100%），即约 8% 的漏检。
   **要不要接受是产品决定，不是技术决定** —— 记在这里等拍板。
2. **全文路收紧候选**：先取查询里 df 最低的 2–3 个 bigram 做 BOOLEAN 预筛（OR 语义），
   再对候选打分。理论上把 3 s 压到几百 ms，但要重新标定（预筛会改变参与打分的集合，
   等于换了个排序函数）。建议先做 1，再做 2。
